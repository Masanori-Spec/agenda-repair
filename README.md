# Agenda Repair

**公開済みの小さなイベント予定を、変更する枠をなるべく少なくして組み直す。**

会場や共有備品が使えなくなったときの、ブラウザ内で動く修復ワークベンチです。元の開始時刻・会場を残し、変更案と差分を並べて確認します。アカウント、サーバー上の計算、外部API、カレンダー連携はありません。

これは小規模な就職活動向けのエンジニアリング作品です。実際の主催者による利用検証・需要検証はまだ行っていません。最適化という手法の新規性や世界初を主張するものではありません。

## 30秒で試す

Node.js 22以上を用意して、このフォルダで実行します。

```sh
npm start
```

表示された `http://127.0.0.1:4174` を開きます。インストール不要です。モジュールWorkerを使用するため、HTMLのファイル直接オープンには対応していません。

1. 合成サンプルを選ぶ
2. 使用不可時間と固定する枠を確認する
3. 修復案を計算する
4. 元の予定との変更一覧・証明状態を確認する
5. 必要なら提案JSONを保存する。外部の予定表は自動変更されません

独自の予定は元データJSONを保存し、その形式に沿って編集して読み込めます。厳格なJSONスキーマのみ受け付けます。提案JSONは監査用で、入力JSONとは別形式です。

## 何を最小化するか

次の優先順位を**辞書式**に比較します。重み付きの合算ではありません。

1. 開始時刻または会場が変わるセッション数
2. 開始時刻の移動量の絶対値合計（分）
3. 会場変更数
4. 同点時はセッションIDのASCII順に、開始分→会場IDのASCII順を比較

会場だけの変更も1枠の変更として数えます。時刻の前倒しと後ろ倒しは同じ絶対移動量です。特定の枠を優遇する重みはありません。

## 守る条件

- 各セッションは1回、元の所要時間のまま配置
- 開始可能範囲・許可された会場・整数分グリッドに従う
- 同じ会場、同じ共有備品は重複利用しない
- 固定した枠の元の時刻と会場を維持
- 会場・備品の使用不可時間に重ならない
- 区間は半開区間 `[開始, 終了)`。10:00終了と10:00開始は重複しない

共有備品は排他的な1台の機材などを表す不透明なIDです。人員配置・採用・評価などの意思決定には使わないでください。実在の個人名・連絡先は必要ありません。

## 結果の読み方

| 内部状態 | 意味 |
|---|---|
| `optimal` | この入力モデルの全候補について最適性を証明。0変更なら理論下限のため即時確定可能 |
| `feasible` | 全制約を満たす案はあるが、探索上限または中断により最適性は未証明 |
| `infeasible` | この有限モデルで実行可能解がないことを証明。現実世界全体で不可能という意味ではない |
| `unknown` | 上限または中断までに案を得られなかった。解なしとは限らない |

独立した検証器が出力の制約を再確認してから表示します。表示する衝突・空候補の説明は診断補助であり、最小矛盾集合の証明ではありません。安全上重要な現場・本番運営では人による確認が必要です。

## 明示的な範囲

| 制限 | 値 |
|---|---:|
| 全セッション | 20件 |
| 変更可能なセッション | 8件 |
| 会場 / 共有備品 | 6 / 8 |
| 使用不可区間 | 24件 |
| 各変更可能セッションの時刻×会場候補 | 120通り |
| 既定探索上限 | 200,000ノード |
| コアAPIの最大探索上限 | 2,000,000ノード |
| 入力JSON | UTF-8で100,000バイト |

整数分による単日（0〜1440分）のモデルです。グリッド幅は1〜60分で、開催日の開始分が起点です。使用不可区間の端点はグリッドに合わせる必要はありません。タイムゾーン、日付、複数日、移動時間、休憩、前後関係、参加者数や会場定員、公平性、分割セッション、繰り返しには対応していません。予定が大きい場合は専用システムを使ってください。

入力上限は探索完了を保証しません。候補数の積は非常に大きくなり得ます。ノード上限は結果の再現性を保ち、Workerの協調yieldと中断機能は画面の応答を保つためのものです。実機での体感速度は未検証です。[測定結果](docs/MEASUREMENTS.md)と[検証の範囲](docs/VERIFICATION.md)を参照してください。

## 設計

- `src/model.js`: 入力サイズ・型・参照整合性・上限を検証。未知のキーを拒否し、元データを変更しない
- `src/solver.js`: 有限領域の分枝限定。使用不可時間を候補から除外し、固定枠を先に配置。残候補数が少ない変数を選択し、辞書式の下界で枝刈り
- `src/verify.js`: ソルバーの候補生成・制約ヘルパーを使わない独立した出力検証
- `src/worker.js`: 別スレッドで計算し、ID付きで進捗・結果・エラーを返す
- `src/app.js`: 元予定と提案を分離し、編集・再計算時に古い計算を無効化
- `src/lifecycle.js`: ページ移動による探索中断を管理。戻った画面で中断を説明し、明示的な再探索を可能にする
- `tests/oracle.js`: 小さな全配置を列挙する別実装。ソルバーや検証器の内部関数を再利用しない

実行時依存はゼロ。状態はメモリ内のみで、再読込すると消えます。ブラウザへの永続保存は行いません。入力は端末から送信されず、アプリの静的ファイルを取得する通信のみが必要です。JSON保存は明示操作です。外部の予定へ書き戻す機能はありません。

## 既存製品との関係

2026-10-03に以下の一次資料を確認しました。

- [Whova Agenda Conflict Checker](https://whova.com/blog/whovas-new-agenda-conflict-checker/) は会場・登壇者・時間帯などの競合を検出します。資料では警告後の並べ替えは主催者が判断する運用と説明されています
- [Sessionize Schedule Builder](https://sessionize.com/playbook/schedule-builder) はドラッグ＆ドロップによる予定作成・会場移動や衝突の確認を提供します
- [Timefold「Responding to change」](https://docs.timefold.ai/timefold-solver/1.x/responding-to-change/responding-to-change) は固定した計画要素や、公開済みの予定の変更へのペナルティを説明しています

この作品で検証する仮説は、「小さな公開済み予定の、元データを保ったままの最小変更修復と根拠確認を、単独の軽い道具にまとめる価値があるか」です。競合が同等機能を一切持たないという主張ではありません。参加登録や登壇者管理に統合済みのツールの方が適する場合もあります。

名前の一般ウェブ検索で明白な同名スケジューラーは見つかりませんでしたが、網羅的調査や商標クリアランスは行っていません。
